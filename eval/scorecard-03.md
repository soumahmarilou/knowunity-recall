# Scorecard 03 — Home chat, Study plan, Mode selection, Free Recall Challenge – Intro

Scope: identical to `eval/scorecard-01.md` and `eval/scorecard-02.md` — `/` (Home chat), `/study-plan` (plus `?progress=50` and `?completed=1&progress=100`), `/recall` (Mode selection — default fallback, custom `?subject=`, and a long-subject overflow probe), `/recall/free-recall-challenge` (Intro/launch — both `entry` values, with/without `subject`). All rendered at 390px, dark mode. Scored against `eval/rubric.md`. Run against the current working tree — both Mode selection's Close button and FRC Intro's whole benefits section have changed substantially since scorecard-02.

Method: (1) every state of each screen was rendered and screenshotted via Playwright (default/typed/empty, tab switches, progress/completed variants, long-subject overflow, pressed via `mouse.down()` + live computed-style diff before/during, a fresh no-history context for both Close buttons across both `entry` values), cross-checked by SHA-256 of PNG bytes and by live computed-style comparison. One methodological correction made mid-pass: Next.js dev mode injects a `<nextjs-portal>` dev-tools overlay in a bottom corner that physically intercepts clicks on whatever sits underneath it — an initial false reading on Study plan's bottom-left nav icon ("no pressed state") was traced to this overlay via `document.elementFromPoint()`, confirmed by hiding the portal (`display: none`) and re-testing, and retracted before being reported as a finding. (2) Four critics — critic-system, critic-craft, critic-ux, critic-ambition — each ran independently in isolated contexts, given only these four screens, `eval/rubric.md`, and their own two dimensions; none saw another critic's output, another critic's dimensions, or this pass's own render findings — each did a genuine first-look pass on the live app.

## Findings, ranked by severity, with evidence

**1. Home's mic/voice-entry button gives zero pressed-state feedback — hard-gate failure, see table above.**
`src/components/ChatInput/ChatInput.module.css:100-136` (`.micButton`), `aria-label="Use voice input"`. Independently confirmed by this pass and by critic-craft. This is the single tap that starts the entire voice-recall feature from Home, and every comparable control elsewhere in scope (ActivityCard, SuperlistItem cards, the current-step button, both Close buttons, the Start button) does depress visibly on the same real-mouse-down test. *Fix: add a minimal `:active` treatment (opacity or the same translateY settle `Button`/`ActivityCard` already use) to `.micButton`.*

**2. Study plan's Plan/Materials tabs give zero pressed-state feedback — hard-gate failure, see table above.**
`src/app/study-plan/page.module.css:115-141` (`.tab`). Found in this pass's own render/diff sweep; no critic independently reproduced this one (see critic-craft's blind spot — their coverage of Study plan's press states centered on the current-step button and the Tertiary "More options" `ButtonIcon`, not the tabs). *Fix: add an `:active` rule to `.tab` distinct from `.tabActive`'s persistent selected-state styling.*

**3. `subject` — the one thing that makes this the student's own exercise — disappears at the Mode selection → FRC Intro hop, and independently, FRC Intro's headline doesn't say what the session is about even though the variable is already in scope.**
Found convergently by **two critics working from different angles**: critic-system (Coherence) rendered all four required variants of FRC Intro and found them byte-for-byte identical in copy regardless of `subject` — `src/app/recall/free-recall-challenge/IntroContent.tsx:55`, `const TITLE = "Say everything you remember before time's up"`, never interpolating the `subject` already destructured at line 61, despite Mode selection one screen earlier doing exactly this (`src/app/recall/ModeSelectionContent.tsx:56`, `` title={`Let's recall ${subject}`} ``). critic-ambition (informational) independently flagged the identical line/fix from a pure source read, citing the same asymmetry with Mode selection. *Fix (per both critics): interpolate `subject` into FRC Intro's title or eyebrow, e.g. `` `Say everything you remember about ${subject} before time's up` `` or `` `Free Recall Challenge · ${subject}` `` beside the eyebrow icon.*

**4. FRC Intro never primes the mic-permission ask, despite voice-ux.md naming this exact screen as the primer — a defect that has persisted through a full copy rewrite.**
critic-ux, against voice-ux.md Principle 3. `src/app/recall/free-recall-challenge/IntroContent.tsx:55-56,84-86` — the title and transparency line explain the exercise mechanic but never mention the microphone, why access is needed, or that typing is available on decline. This is the same defect scorecard-02 found (finding #5) on this screen's old three-benefit-row copy; the whole section has since been rewritten (see scope note above) but the underlying gap survived the rewrite untouched. *Fix: one line before Start, e.g. "We'll ask to use your mic — you can type instead any time."*

**5. Home's entire bottom nav bar has zero accessible name on every icon-only button.**
critic-ux (Accessibility). `src/components/NavigationButton/NavigationButton.tsx:26-36` — `NavigationButtonProps` has `label` and `hasLabel` (whether to *show* it) but no `ariaLabel` prop, so when `hasLabel={false}` (Home's all four nav buttons, `src/app/page.tsx:129-137`), the rendered `<button>` gets no visible text and no `aria-label` fallback — no accessible name at all. Contrasts with `AppBar`'s icon buttons, which do take and correctly render `leftAriaLabel`/`rightAriaLabel` (verified via `getByLabel("Close")` resolving correctly in the same critic's click-through). A structural gap in the component's own API, not a one-off miss at a call site.

**6. The same "Recall exercice" identity icon renders as two visually unrecognizable versions of itself, one screen apart, and it's undisclosed.**
critic-system. On Home, `Flask01` renders as its native two-tone coral/orange glyph inside `ActivityCard` (`src/app/page.tsx:90`, no color override in `ActivityCard.module.css`). On Study plan, the same icon component inside the current-step `ButtonIcon` (`src/app/study-plan/StudyPlanContent.tsx:258`) flattens to a solid monochrome silhouette because `ButtonIcon.module.css:44-45` forces `fill: currentColor` on every descendant path, collapsing the two-tone illustration. Confirmed by rendering and cropping both instances. Not logged in `component-gaps.md` despite the file logging smaller gaps. *Fix: either give `Flask01` a single-tone `currentColor`-only rendering, disclose the loss in `component-gaps.md`, or use a purpose-built single-tone glyph for the current-step icon.*

**7. Home's activity-card row has a measurable icon-alignment defect in its own default render — not an edge case.**
critic-craft. `src/components/ActivityCard/ActivityCard.module.css:35-36` centers each card's icon+label block inside a fixed-height card. Because "Recall exercice" wraps to two lines while its siblings ("Flashcards," "Quizz") fit on one, the icon sits **15px from the card top on two-line cards vs. 27px on one-line cards** (`getBoundingClientRect()` diff, confirmed visually) — with real, shipped label text, not a contrived string. *Fix: give `.card` a fixed icon slot instead of centering the whole icon+label group as one block.*

**8. A realistic multi-sentence typed message breaks Home's "pinned to bottom" chat input layout.**
critic-craft. `src/components/ChatInput/ChatInput.module.css:1-4` (`.root { align-items: center }`) centers the `+`/send icons against the whole grown textarea height; a 6-sentence typed message pushes the entire bottom cluster (chips, input, nav bar) to `top: 1166px` — 322px below the 844px viewport (`document.body.scrollHeight` grew to 1237px) — directly contradicting the page's own comment that this cluster is pinned to the bottom. *Fix: `align-items: flex-start` (or `align-self: flex-end` on the icons) plus a `max-height`+scroll cap on the textarea's auto-grow.*

**9. Mode selection's long-subject overflow, first found in scorecard-01, is still unfixed two scorecards later.**
This pass: navigating to `/recall?subject=<83-char string>` produced `document.documentElement.scrollWidth = 866` against a 390px viewport. `TextBlock.module.css` is unchanged since scorecard-01/02 — still `width: fit-content` with no `overflow-wrap`/`word-break` on `.title`. FRC Intro is not a reproducer for this anymore: its title is now fully hardcoded and never receives `subject` at all (see finding #3), so it has no overflow risk, but also no personalization. *Fix, unchanged since scorecard-01: `max-width: 100%; overflow-wrap: break-word;` on `.title`, plus `min-width: 0` on its container.*

**10. Mode selection's three mode cards read as undifferentiated, even though one mode is structurally different (it's the only clocked one).**
critic-ambition. `src/app/recall/ModeSelectionContent.tsx:63-95` renders all three `SuperlistItem` rows identically apart from icon/color/descriptor prose. Free Recall Challenge is the only timed mode — `src/app/recall/free-recall-challenge/frc.ts:34` already hardcodes "You have 1 minute" as real session content. `Chips` (`color="Primary"`, `size="XXS"`) is already cataloged for exactly this ("short status labels") and uses a real interactive token, not `accent/1-4`. *Fix: a small `Chips` badge ("1 min") composed alongside the FRC row.*

**11. Knowie's copy register shifts between two adjacent screens.**
critic-system, lower-confidence/supporting evidence (a register judgment, not a rendering diff). Mode selection: warm/collaborative ("Let's recall {subject}"). One screen later, FRC Intro: flat imperative title plus a third-person, faintly surveillance-toned transparency line ("Knowie checks how many of the lesson's topics you actually mention"). Flagged as supporting evidence for the Coherence score, not a primary finding.

**12. Study plan's Tertiary "More options" icon button gives no press feedback, inconsistent with its Secondary sibling two rows away.**
critic-craft. `ButtonIcon.module.css`'s `.variantTertiary` has no `:active` rule at all — disclosed in the component's own comments as intentional (matches Figma, which defines no Tertiary pressed state), so this is lower severity than findings #1–2, but it still means two icon buttons on the same screen give visibly inconsistent tactile feedback to a student who can't see the source comment explaining why.

**13. Two of Home's four bottom-nav icons are dead taps with no destination.**
critic-ux. `src/app/page.tsx:130,137` — `SearchMd` and `Trophy02` nav buttons have no `onClick`. Not a Must-tier voice-ux state and not a hard-constraint trap (optional chrome, not a required step), but a tap produces literally no response, which brushes against Principle 1's "system status must always be obvious." Lowest severity of the findings above.

**14. Positive, verified findings — real fixes holding under adversarial testing.**
- **The Close-button trap from scorecard-01/scorecard-02 is now genuinely fixed**, confirmed by three independent parties this round (this pass, critic-system, critic-ux): a fresh no-history browser context (`window.history.length === 2` immediately after `page.goto()`) on both Mode selection and FRC Intro, for both `entry=home` and `entry=study-plan`, resolves correctly (`/` or `/study-plan?progress=0`) instead of dead-ending at `about:blank`. `src/lib/entryPoint.ts`'s `studyPlanCloseUrl()` uses an explicit `router.push()` destination rather than `router.back()`, which is why it holds regardless of history.
- `entry` now threads correctly end-to-end (Close and Start on both in-scope Close/Start controls), verified live by critic-system and critic-ux.
- The `Screen` shell's 16px top/bottom inset measures identically (`getComputedStyle`, not inferred) across all four screens.
- Done/current/locked states on Study plan and BadgeChip's three types are confirmed not color-only — each pairs its color with a distinct icon and secondary treatment (critic-ux, rendered).

## Each critic's blind spot

- **critic-system** — scope excluded Guided Reflection's and Concept Questions' own Intro screens, so can't confirm whether the `subject`-drop (finding #3) or the copy-register shift (finding #11) are FRC-specific or recur across all three modes' Intros. Also didn't check whether `Flask01`'s color-flattening (finding #6) recurs anywhere else the icon is used outside these four screens.
- **critic-craft** — could not test on a real touch device; `useDragScroll` (`src/lib/dragScroll.ts`) explicitly only intercepts `pointerType === "mouse"` and leaves touch to native scroll, so mouse-based Playwright presses on the horizontally-scrolling activity/quick-action rows may not reflect real finger drag-vs-tap disambiguation — relied on the code's own stated intent rather than a verified touch trace.
- **critic-ux** — scope excluded all six of voice-ux.md's Must-tier states that live downstream of these four screens (Recording, Processing, Result, Cancel & re-record, Text fallback, Permission denied) — none of the four in-scope screens contain any session/recording UI, so this critic has no evidence either way on most of the checklist. Also tested only headless Chromium at fixed viewport/dark-mode — can't speak to how the near-floor `Step N` contrast (4.60:1 measured) holds up under real iOS Safari font smoothing, the actual target platform.
- **critic-ambition** — did not render anything; every proposal comes from a static read of `.tsx`/`.module.css` source against `design-system_1.md` and Storybook docs. If any screen behaves differently at runtime than its source suggests, that would not be caught here.
- **This pass (phase 1 / reconciliation)** — relied on critic-ux's own contrast and touch-target measurements rather than independently re-measuring every pairing; cross-checked directly only the two hard-gate press-state findings and the Close-button fix. The Next.js dev-tools portal overlay (see Method) is a known hazard specific to testing in dev mode — a production build wasn't tested, so this can't rule out other portal-shaped false negatives in areas not manually cross-checked with `elementFromPoint()`.

## Critic-ambition's read (informational — not part of the weighted total)

**5/10.** One screen in this four-screen scope takes a real swing; the other three settle for the default composition even where the same codebase already proves a cheaper, stronger option works — that balance lands this at the pinned floor, not above it. Study plan (`src/app/study-plan/StudyPlanContent.tsx:206-290`) is the one real swing: the alternating `stepOffset` stagger reads as a winding path rather than a plain list, and the current step pairs `ButtonIcon` with a pulsing `ProgressRing` to invite a tap — a genuinely stronger arrangement of two real components. That ambition doesn't carry into the other three screens. Three proposed patterns, each built only from components verified to exist and already instantiated elsewhere in this app:
1. `MascotSlot`'s own `animate` bounce-in prop (already wired and live on all three modes' completion screens) is unused on Home's and Mode selection's hero mascots, even though both are genuine one-time arrivals — the exact category the project's own motion rule reserves real motion for.
2. Mode selection's three `SuperlistItem` rows read as undifferentiated despite Free Recall Challenge being the one structurally different (clocked) mode — a `Chips` badge ("1 min"), already cataloged for exactly this use, would surface that difference using data the app already has.
3. FRC Intro's hardcoded title doesn't interpolate `subject`, even though the variable is already in scope two lines above it — the identical component one screen back (Mode selection) already does this correctly. (Independently converged upon by critic-system too — see finding #3 above.)
